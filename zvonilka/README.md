## Почему сейчас один worker

У каждого процесса своя память. Например:

```text
Worker 1: соединение Алисы, её Outbox, локальный ParticipantsHub
Worker 2: соединение Боба, его Outbox, другой ParticipantsHub
```

Алиса и Боб могут попасть в разные процессы. Тогда каждый процесс видит только своего участника: общий Redis хранит admission и presence, но сам по себе не доставляет сообщения в очереди другого процесса. Это обычное ограничение in-memory WS-менеджеров при нескольких workers или репликах.

Для нашей реализации это означает:

- неполные снимки `participants`;
- невозможность напрямую переслать сообщение адресату другого worker;
- невозможность одним локальным `Connection.stop()` остановить старое соединение в другом процессе.

Позже понадобится межпроцессная доставка, например через Redis Pub/Sub, плюс согласование поколений, порядка снимков и восстановления после пропущенных событий. Просто добавить `-w 4` недостаточно. Межпроцессный брокер — стандартный способ связать локальные WS-реестры.

Поэтому сейчас фиксируем: **один процесс API и одна его реплика**. Четыре контейнера с одним worker в каждом создали бы ту же проблему.

## 1. Обновление токена — не связано со входом второго участника

Отдельного токена комнаты не будет. Каждый клиент использует access JWT своей сессии.

Схема такая:

```text
Срок собственного JWT подходит к концу
→ клиент через HTTP refresh получает новый JWT
→ отправляет его по существующему WS: reauthenticate
→ сервер подтверждает обновление
```

Подключение другого участника этого не запускает. Обновление выполняется в фоне, без повторного ввода пароля — для этого и используется refresh token.

Наша цель: без переподключения WS, повторного join и изменения поколения. В штатном случае пользователь ничего не заметит; при ошибке обновления потребуется обработка в клиенте.

## 2. Выход из комнаты — без ожидания 10 секунд

Ты прав: при нажатии «Выйти из комнаты» клиент сразу прекращает локальный звонок и закрывает WS. Сервер после получения disconnect убирает присутствие и публикует новый `participants`. Искусственного ожидания здесь не будет. Закрытие WS уже имеет специальный протокольный механизм — отдельное JSON-сообщение «я отключился» для этого не обязательно.

Если сеть пропала или процесс аварийно завершился, уведомление может не прийти — тогда нужен существующий heartbeat/lease-механизм.

**10 секунд** — исключительно период проверки _отзыва авторизационной сессии_: например, пользователь на другом устройстве нажал «Завершить эту сессию». Это не таймер выхода из комнаты.

Для logout на текущем клиенте также не ждём проверки: сам клиент сразу закрывает свой WS.

## 3. Что означают 30 секунд

Это запасное окно, если JWT уже истёк, а клиент не успел обновиться:

- WS временно остаётся открыт;
- heartbeat и `reauthenticate` разрешены;
- SDP/ICE для этого соединения приостановлены;
- новый JWT принят — работа продолжается;
- за **30 секунд** обновления нет — закрываем WS.

Это не обязательная пауза при каждом обновлении. Нормальный клиент обновляется заранее и в это окно вообще не попадает.

Итого: вход другого участника ничего не обновляет; обычный выход обрабатывается сразу; 10 секунд относятся к внешнему отзыву сессии, 30 — только к восстановлению просроченной авторизации.

## 10 секунд — проверка отзыва, не refresh

Раз в 10 секунд сервер сам проверяет в БД: «Эту авторизационную сессию ещё не завершили принудительно?»

При этом:

- клиент ничего не обновляет;
- новые JWT не выпускаются;
- срок существующего JWT не продлевается.

Refresh происходит отдельно, ближе к истечению access token. Он получает новый токен, а `reauthenticate` сообщает уже открытому WS: «Теперь используй вот этот новый токен». Это не heartbeat и не продление старого JWT.

То есть период проверки отзыва — 10 секунд, а период refresh определяется сроком JWT, а не этим таймером.

## Что такое поколения

Поколение (`generation`) — уникальный идентификатор конкретного подключения пользователя к комнате, не версия токена.

Пример:

```text
Первое подключение → generation A
Переподключение    → generation B
```

После замены актуально только B:

- запоздалый disconnect от A не удалит присутствие B;
- сообщение, адресованное A, не попадёт автоматически в B;
- старое окно не сможет отправлять сообщения от имени нового подключения.

При успешном `reauthenticate` того же WS поколение не меняется: соединение осталось прежним, поменялось только подтверждение авторизации.

Коротко: JWT — право доступа; сессия — конкретный вход в аккаунт; поколение — конкретное подключение к комнате.
