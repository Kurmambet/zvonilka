# Signaling v1: heartbeat, замена поколения, shutdown (поставка 3)

Этот документ заменяет ограничение короткой сессии из поставки 2.
Вход и существующие REST/admission/Lua остаются прежними. Redis transaction.lua
не изменяется. API по-прежнему запускается в одном процессе/worker/event loop.

## Что изменилось в контракте

В joined добавлены числовые поля:

- heartbeat_interval_ms — рекомендуемый интервал отправки клиентом;
- heartbeat_timeout_ms — серверный скользящий бюджет ожидания heartbeat.

При presence_ttl=45 и Policy по умолчанию сервер отправляет 7500 и 22500 мс.
Поля имеют значения по умолчанию в модели для совместимости имеющихся fixtures,
но живой сервер всегда указывает вычисленные значения. Это не разрешение клиенту
настраивать lease и не остаток времени, измеренный от момента доставки joined.
Сервер отсчитывает консервативный бюджет от начала Redis join/heartbeat.

Бюджет: min(Policy.heartbeat_timeout, presence_ttl/2). Рекомендация клиенту:
min(10 секунд, бюджет/3). Регулярный успешный heartbeat сдвигает бюджет; общего
20-секундного таймера больше нет. Сам lifetime комнаты heartbeat не продлевает.

После joined клиент отправляет текстовый JSON:

```json
{
  "version": 1,
  "type": "heartbeat",
  "request_id": "00000000-0000-4000-8000-000000000001",
  "generation": "00000000-0000-4000-8000-000000000002"
}
```

Здесь generation — значение, полученное в joined; это не новое поколение,
выбираемое клиентом. Сервер сверяет его с Attempt, а в Redis передаёт только
сохранённые серверные user_id, room_id и generation. Эти ID не берутся из heartbeat.
Лишние поля, включая user_id, room_id, access_token, отклоняются.

Ответ после успешного Redis heartbeat:

```json
{
  "version": 1,
  "type": "heartbeat_ack",
  "request_id": "00000000-0000-4000-8000-000000000001",
  "generation": "00000000-0000-4000-8000-000000000002"
}
```

Клиент должен отправлять heartbeat с рекомендуемым интервалом и сопоставлять ack
с request_id/generation, без параллельного бесконтрольного потока запросов.
HeartbeatAck подтверждает только присутствие; это не проверка WebRTC-медиа,
не обновление JWT и не новый снимок участников.

Минимальный локальный интервал обработки:
min(Policy.heartbeat_min_interval, бюджет/4), по умолчанию 0.25 секунды.
Более частое сообщение отклоняется rate_limited с завершением соединения.
Это небольшой предохранитель Redis в текущем протоколе, не полноценный per-IP
rate limiter. Ограничения сообщения, WS backend и числа подключений сохранены.

Authenticate остаётся первым сообщением. После входа пока допустим только
heartbeat. Offer/answer/ICE и события участников ещё не реализованы.
client_message_adapter теперь возвращает union Authenticate | Heartbeat;
перед доступом к специфичным полям необходимо сужение типа.

## Ошибки

Добавлены конечные публичные коды:

| Код                 | Значение                                                   |
| ------------------- | ---------------------------------------------------------- |
| heartbeat_timeout   | Не получен допустимый heartbeat в пределах бюджета         |
| connection_replaced | У того же аккаунта в той же комнате успешно вошёл новый WS |
| server_shutdown     | Сервис прекращает обслуживать соединение                   |

Все три в текущей поставке fatal. Shutdown закрывается кодом 1012,
замена/timeout — 1008. Unsolicited ошибки connection_replaced/server_shutdown
всегда имеют request_id=null. Ошибка валидного heartbeat коррелируется его ID;
ошибка malformed JSON/ожидания без сообщения — null.

Неправильное поколение — stale_generation, Redis не вызывается.
Ошибки Redis/timeout операции — dependency_unavailable, без ложного ack и без
локального сдвига deadline. Schema mismatch также не является успехом.
Если закончился безопасный бюджет во время Redis-операции, ack не выдаётся,
хотя сама операция уже могла успеть примениться; затем выполняется cleanup.

## Одно окно заменяет другое

Локальный реестр ключуется парой (проверенный user_id, room_id).
Per-key asyncio.Lock сериализует join и heartbeat, но не сетевые отправки.
Разные аккаунты/комнаты не ждут этого lock друг у друга.
Реестр и очереди ожидающих операций ограничены живой работой; gate удаляется,
когда нет владельца и ожидающих/исполняющихся операций.

После успешного Redis join и валидации снимка новый Attempt становится локальным
владельцем. Старому Connection выставляется stop-event connection_replaced.
Ожидание его входного сообщения/операции прерывается, поэтому ждать очередного
heartbeat старого окна не требуется. Дочерние задачи работы и stop-waiter
отменяются/дожидаются в finally; не создаётся отдельный бесконечный heartbeat task.

Новый join не ждёт медленной отправки старому клиенту. Старый cleanup использует
ТОЛЬКО своё поколение, и не удаляет нового владельца локального реестра даже при
ошибке Redis. Атомарный generation fence в существующем Lua защищает само presence.
Уже отправленный до замены joined/ack не может быть отозван из сети; клиент должен
учитывать закрытие старого соединения и поколение, а не считать старый ack новым входом.

Если join завершился с неизвестным результатом, мы не утверждаем, что старое
подключение осталось текущим в Redis: его следующий heartbeat может получить
stale_generation. Делается прежняя best-effort попытка leave своего поколения;
при недоступности Redis окончательным предохранителем остаётся lease expiry.

## Остановка

Все обслуживаемые обработчики, включая ожидающие авторизацию, регистрируют
Connection. service.shutdown():

1. Запрещает новые acquire.
2. Ставит stop-event всем зарегистрированным соединениям.
3. Ждёт их done в пределах Policy.shutdown_timeout (по умолчанию 10 секунд).

Обработчик закрывает WS и делает ограниченный cleanup, затем снимает локальный
учёт и сигнализирует done. При timeout shutdown явно завершается TimeoutError,
а не объявляет успешное завершение всех обработчиков. Повторный shutdown после
завершения обработчиков допустим. Принудительная остановка процесса, повторная
отмена и код зависимости, игнорирующий cancellation, не превращаются в гарантию
немедленного leave; graceful-сценарий требует кооперативной отмены зависимостей.

В api.py shutdown вызывается перед закрытием Redis/engine. Важно: это shutdown
lifespan приложения, а не обработчик OS signal. Uvicorn сначала сам закрывает
соединения/drain-ит обработчики, затем завершает lifespan. Поэтому не следует
ожидать JSON server_shutdown на каждый SIGTERM: клиент может получить обычное
серверное WS-закрытие. Добавлен loopback-тест остановки реального Uvicorn.
Не заменять запуск несколькими workers и не считать этот механизм брокером.

## Граница поставки

JWT/session проверяются при входе. Reauthentication, периодическая проверка отзыва
сессии и политика истечения access token ещё не реализованы. Heartbeat не отменяет
эту задачу и не означает, что текущий WS готов к публичной эксплуатации.

Не реализованы: события участников/их порядок, SDP/ICE, REST close broadcast,
reconnect клиента, Electron, TURN и длительный реальный звонок. Закрытие комнаты
может обнаружиться через отказ последующего Redis heartbeat, но это не broadcast.

Новых зависимостей и миграций нет. Legacy WS backend Uvicorn в этой поставке
не меняется; его deprecation warning не подавляется.

## Тесты

Сохранены прежние проверки и обновлена только семантика старого 20-секундного
таймера: теперь отсутствие heartbeat даёт heartbeat_timeout, а периодические
heartbeat позволяют пережить исходный бюджет.

- schemas: прежние 18, с явным narrowing для расширенного client adapter.
- service: прежние 13, с актуальным heartbeat budget и cleanup-поведением doubles.
- presence_unit: 18 новых проверок схем, ack/fencing, overlapping joins,
  отмены waiter, позднего leave, ошибок продления, rate limit, shutdown и очистки gates.
- transport: прежние 17, включая обновлённый idle timeout.
- presence_transport: 7 новых ASGI-проверок длительного presence, замены сокета,
  Redis-ошибки, устаревшего поколения и shutdown с остановкой ожидающих операций.
- network: теперь 4, включая heartbeat и остановку Uvicorn через настоящий TCP.
- integration: теперь 8; новые проверки на реальном Redis/PostgreSQL включают
  heartbeat дольше исходного TTL, позднее старое поколение, idle timeout и shutdown.

Doubles в unit/ASGI/network не доказывают атомарность Redis. Реальная интеграция
нужна отдельно; реальные сети/трёхчасовой звонок эти тесты не заменяют.

# Поставка 4.1: ограниченная очередь и один отправитель

Это отдельная законченная часть этапа, а не весь этап событий участников.
Добавляются только два файла: signaling/outbox.py и tests/test_signaling_outbox.py.
Существующие WS router/service/schemas, Redis, авторизация и зависимости не меняются.
Новая очередь ПОКА НЕ ПОДКЛЮЧЕНА к рабочему WS: поведение приложения не изменится.
Подключение к router и room events будет следующей поставкой после проверок.

## Применение

Распаковать ZIP в корень проекта, где находятся pyproject.toml и zvonilka/.
Patch не нужен: оба файла новые. При существующем outbox.py остановиться,
не перезаписывать неизвестную версию.

```bash
uv run ruff format src/zvonilka/signaling/outbox.py tests/test_signaling_outbox.py

```

## Контракт

TextSink совместим по используемым методам с send_text(data) / close(code).
Outbox.start() создаёт ровно одну writer-задачу. Только эта задача вызывает sink.
Вызов offer(text) синхронный: очередь не ожидается. True означает постановку,
НЕ подтверждение доставки. False означает закрывающуюся очередь/переполнение.

Capacity по умолчанию 32: это максимум ОЖИДАЮЩИХ сообщений; отдельно может быть
одно in-flight сообщение. Каждое ограничено 16384 UTF-8 байтами. При завершении
может быть одно отдельное ограниченное final_message. Это предел payload,
не точная оценка RAM Python и не ограничение всех очередей/сокетов процесса.

Переполнение: очередь очищается, новые сообщения не принимаются, запрашивается
закрытие 1013. Зависшая отправка ограничена send_timeout (по умолчанию 2 секунды).
Ошибка отправки закрывает с 1011; timeout — 1013. Закрытие имеет отдельный
close_timeout (2 секунды). Исключения транспорта не сохраняются/не логируются:
failure — только конечный код причины. Неизвестные исключения не выходят из writer,
но видны как send_failed / close_failed; CancelledError не проглатывается.

request_close/aclose не drain: ожидающие сообщения отбрасываются, чтобы не слать
устаревшие события после замены/закрытия. Опциональный final_message отправляется
перед close при отсутствии ошибки транспорта, со своим send_timeout. Первое
закрытие сохраняет причину/код; последующие вызовы не подменяют его.
Уже начавшаяся отправка может закончиться после request_close: её нельзя отозвать.
Общий путь close может включать остаток in-flight send + final send + close,
то есть до 2\*send_timeout + close_timeout при кооперативной отмене транспорта.

Отмена wait_closed не отменяет writer: используется shield. После отмены ожидания
владелец должен всё равно запросить close и дождаться завершения при cleanup.
Нельзя вызывать sink.send_text/close параллельно с работающим Outbox: при интеграции
в router все пути отправки и закрытия нужно перевести на одного владельца.

Это ещё не room coordinator, порядок snapshot/events или протокол участников.
Тесты используют transport double, а не настоящий WebSocket/TCP. Порядок FIFO,
backpressure, таймауты, изоляция медленного получателя и lifecycle проверяются
независимо; фактическая WS-интеграция будет проверяться отдельно.
