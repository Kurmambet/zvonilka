# Signaling v1: контракт входа (поставка 1)

Статус: реализованы только Pydantic-схемы и unit-тесты. WS endpoint,
аутентификация транспорта, admission, таймеры и доставка сообщений пока не реализованы.
Документ не является подтверждением работающего signaling.

## Граница текущей поставки

Модуль: `zvonilka.signaling.schemas`.

- Клиент: `Authenticate`, `client_message_adapter`.
- Сервер: `Joined`, `Error`, `server_message_adapter`.
- `version` обязателен и равен целому `1`, без преобразования строк/float/bool.
- Направления сообщений разделены. Неподдерживаемые типы и лишние поля
  верхнего уровня отклоняются.
- Приёмник не должен возвращать наружу текст `ValidationError`, `errors()`,
  исходный JSON или непроверенные исключения: они могут содержать access token.
- UUID в JSON передаются строками; серверная сериализация выдаёт каноническую форму.

Вложенный `room` использует существующий `rooms.schemas.RoomView`, без изменения
REST-схемы. Это внутренний серверный снимок, а не разрешённый клиентский ввод.
`RoomView` сохраняет собственные настройки валидации: запрет лишних полей
внешнего envelope не делает вложенную существующую модель строгой.

## Планируемый порядок входа

1. Клиент открывает WS без токена в URL.
2. Первое прикладное сообщение — `authenticate`.
3. Сервер проверяет сообщение, затем вызывает существующий
   `AuthService.authenticate(access_token)`.
4. Идентичность берётся только из возвращённого `Principal`.
5. Сервер создаёт UUID поколения и вызывает существующий `RoomRepository.join`.
6. Только после успешного join сервер возвращает `joined` с его снимком.

Точный URL endpoint, сроки ожидания, транспортные лимиты и коды закрытия будут
введены вместе с WS endpoint. Схемы сами не ограничивают время подключения,
размер WS frame, частоту сообщений или количество одновременных подключений.

Создание комнаты/погашение приглашения не заменяет join. Ошибка Redis/БД
не должна приводить к `joined`. Поколение не принимается от клиента при входе.

## Клиент → сервер: authenticate

```json
{
  "version": 1,
  "type": "authenticate",
  "request_id": "00000000-0000-4000-8000-000000000001",
  "room_id": "00000000-0000-4000-8000-000000000002",
  "access_token": "<access JWT>",
  "app_version": "0.5.0-dev.1",
  "capabilities": []
}
```

Все поля обязательны. `request_id` создаёт клиент для корреляции этого входа;
это не credential, не ключ идемпотентности Redis и не порядок событий комнаты.
`room_id` должен обозначать комнату, к которой аккаунт уже допущен.
Приглашение погашается через существующий REST, не в WS handshake.

- `access_token`: 1–4096 символов; JWT и действующая сессия проверяются
  AuthService, а не схемой. Нижняя граница не означает, что любой такой токен валиден.
- `app_version`: 1–64 ASCII-символа; первый — буква/цифра, далее также `.`, `+`,
  `_`, `-`. Это идентификатор сборки, не строгий SemVer и не версия протокола.
- `capabilities`: явный список из 0–16 уникальных имён длиной 1–48 символов.
  Имя начинается со строчной ASCII-буквы, далее допустимы `a-z`, `0-9`, `_`, `.`, `-`.
- Неизвестное синтаксически корректное capability принимается, но не включается
  автоматически. Это обеспечивает расширение без неявного разрешения функций.
- `user_id`, `session_id`, `generation` в сообщении входа запрещены.

`SecretStr` скрывает токен в repr и стандартной JSON-сериализации модели.
`model_dump_json()` модели Authenticate поэтому НЕ является способом отправки
настоящего токена: отправитель должен явно извлечь `get_secret_value()` и
сформировать wire payload на доверенной границе. Модель не логировать; сырые
validation errors также не логировать. Приёмник не должен хранить токен дольше,
чем необходимо для дальнейшей политики WS-авторизации.

## Сервер → клиент: joined

```json
{
  "version": 1,
  "type": "joined",
  "request_id": "00000000-0000-4000-8000-000000000001",
  "user_id": "00000000-0000-4000-8000-000000000003",
  "generation": "00000000-0000-4000-8000-000000000004",
  "room": {
    "room_id": "00000000-0000-4000-8000-000000000002",
    "owner_id": "00000000-0000-4000-8000-000000000003",
    "state": "active",
    "revision": 2,
    "members": [
      {"user_id": "00000000-0000-4000-8000-000000000003", "online": true}
    ],
    "activated_at": null,
    "deadline": null,
    "empty_at": null
  },
  "capabilities": []
}
```

`request_id` повторяет ID принятого authenticate; `user_id` — Principal,
`generation` — UUID, созданный сервером для этого подключения. Снимок должен
относиться к запрошенной комнате. Эти межсообщенческие соответствия проверит
будущий обработчик; отдельная Pydantic-модель их проверить не может.

Схема дополнительно требует active-комнату, 1–3 уникальных участников и
присутствие собственного `user_id` с `online: true`. Порядок members берётся
из существующего репозитория, не перестраивается signaling-схемой.
Nullable-времена сохранены совместимыми с RoomView; транспорт должен использовать
реальный снимок репозитория, а не генерировать время самостоятельно.

Ответный capabilities — список согласованных функций: пересечение известных
серверу поддерживаемых возможностей и запроса клиента. В этой поставке
функциональные capability ещё не зарегистрированы; ожидаемый ответ — `[]`.
Схема проверяет формат/уникальность, но не выполняет согласование сама.

`room.revision` — ревизия состояния комнаты, не счётчик WS-сообщений и не
поколение подключения. Порядок начального снимка и последующих событий должен
обеспечить будущий transport/coordinator. Подтверждение joined не доказывает
наличия медиа, TURN-маршрута или успешного WebRTC negotiation.

## Сервер → клиент: error

```json
{
  "version": 1,
  "type": "error",
  "request_id": null,
  "code": "invalid_message",
  "fatal": true
}
```

`request_id` обязателен, но может быть null, когда корреляцию нельзя безопасно
установить (например, сломанный JSON или истечение времени первого сообщения).
Если принятая схема запроса содержит корректный ID, сервер возвращает его.
Нельзя копировать произвольное значение ID из невалидного JSON без проверки.

`fatal` — строгий boolean. true означает, что сервер завершает это соединение;
false — ошибка сообщения без завершения соединения. Все ошибки первоначального
входа планируются fatal. Внутренние детали и свободный текст отсутствуют.

Конечный перечень кодов в текущей модели:

| Категория | Коды |
| --- | --- |
| Протокол | `invalid_message`, `unsupported_version`, `message_too_large` |
| Авторизация | `authentication_required`, `authentication_timeout`, `invalid_access` |
| Комната | `room_not_found`, `room_closed`, `not_admitted`, `stale_generation` |
| Квоты | `room_limit`, `owner_room_limit`, `participant_limit`, `overloaded`, `registry_full`, `rate_limited` |
| Зависимости / сервер | `dependency_unavailable`, `internal_error` |

Будущий обработчик отличает целочисленную неподдерживаемую версию
(`unsupported_version`) от отсутствующей/неправильного типа (`invalid_message`).
В этой поставке адаптеры просто выбрасывают ValidationError: преобразователь
в wire error ещё не реализован. Неизвестная Redis schema и недоступность Redis/БД
публично отображаются в `dependency_unavailable`; неизвестный внутренний код —
в `internal_error`. Это правила для будущего обработчика, не готовый error mapper.

## Сознательно не реализовано

- WS endpoint, accept/close, timeout авторизации и ограничения frames/очередей.
- Реальный join, защита от нескольких окон, heartbeat, leave и lease cleanup.
- Reauthentication/отзыв сессии и восстановление.
- События участников и их упорядочивание относительно снимка.
- SDP/ICE, metadata дорожек, perfect negotiation и клиент.

Контракт этих сообщений не разрешает игнорировать поколения при последующей
доставке SDP/ICE. Форматы будущих сообщений будут добавляться отдельной поставкой.

## Проверки

Из `zvonilka/backend/`:

```bash
uv run python -m zvonilka.testing.runner --start tests --pattern test_signaling_schemas.py --require-no-skips
uv run ruff format --check src/zvonilka/signaling tests/test_signaling_schemas.py
uv run ruff check src/zvonilka/signaling tests/test_signaling_schemas.py
```

Это unit-проверки контракта, не транспортные тесты. Redis/PostgreSQL не нужны.
