# Redis admission и приглашения

## Почему один ограниченный aggregate

Для стартовой вместимости в две комнаты выбрана одна JSON-запись Redis,
изменяемая одной Lua-транзакцией. Это минимизирует риск рассогласования
индексов, токена приглашения, места допуска и счётчиков при сбое.
Операции используют серверное TIME. Клиент не задаёт время.

Один скрипт читает запись, чистит leases/сроки, проверяет запрос и пишет её
одним SET после сериализации. Ошибка до SET не записывает частичное состояние.
Отклонённая операция не сохраняет побочную уборку; следующая операция повторит
её, опираясь на серверное время. Вызов sweep отдельно сохраняет уборку.

Цена решения: O(число комнат + присутствий), сериализация всей записи и
блокирование Redis на время Lua. Ограничения max_records <=128 и
invites_per_room <=32 проверяются Python-границей. Это не масштабируемое решение
для тысяч комнат. Перед production нужен benchmark худшего разрешённого состояния.
Скрипт не является доступным пользователям API: Redis закрыт сетью и ACL,
никто извне не должен иметь возможность вызвать EVAL с произвольной конфигурацией.

Закрытые записи удаляются через 24 часа после фактической фиксации закрытия.
Это даёт ограниченную историю идемпотентности, но означает потенциальный
отказ registry_full при интенсивном создании/закрытии комнат. Отказ явный;
увеличивать лимит без замера задержки Lua запрещено. В production дополнительно
нужны rate limits. История приглашений ограничена 32 на комнату, после чего
возвращается invite_history_limit, а не неограниченный рост записи.

## Состояния и сроки

- created: pending TTL от создания, активный слот не занят.
- active: первый join атомарно проверяет global/owner квоты и ставит deadline.
- recovering: последний leave или истечение последнего presence lease;
  слот удерживается ещё grace секунд.
- closed: owner close, истечение pending/lifetime или окончание grace.

Lifetime/grace/retention фиксируются при создании комнаты, lifetime начинает
отсчитываться при активации. Изменение этих настроек не меняет существующие
комнаты. Глобальные/owner квоты и participants используются из текущего
конфига. Снижение квот не закрывает и не вытесняет допущенных участников.

Presence lease по умолчанию 45 секунд. В будущем API heartbeat должен его
продлевать примерно раз в 10 секунд. Heartbeat не обновляет lifetime комнаты.
После рестарта API повторный join восстанавливает presence, если не истёк grace.
Sweeper нужен примерно каждые 5 секунд; его подключение к lifespan API ещё не
реализовано. Любая операция также выполняет логическую уборку перед проверками.

При поздней уборке grace начинается с expiry последнего lease, не с момента
sweep. Heartbeat, пришедший после expiry, требует нового join. Скрипт возвращает
stale_generation; старое соединение не должно воскрешать lease новым heartbeat.

## Несколько окон/устройств

Допуск привязан к UUID аккаунта, а presence к UUID поколения WS-соединения,
созданному сервером. Новый join заменяет старое поколение и возвращает его
ID для закрытия старого WS. Старые leave/heartbeat получают stale_generation.
Повтор join с тем же поколением не возвращает команду замены самого себя.
В реальном signaling также нужен fencing адресной доставки; он пока отсутствует.
Повтор leave не меняет состояние и возвращает stale_generation, а не продлевает grace.

## Приглашения

secrets.token_urlsafe(32), в Redis только SHA-256 токена. Выдача только владельцу.
Количество одновременно действующих непогашенных ссылок не превышает число
ещё не допущенных участников. Выдача не активирует комнату и не занимает слот.
Метода просмотра, расходующего приглашение, нет.

Redeem: проверка комнаты, токена, TTL/отзыва и вместимости, создание допуска и
пометка consumed выполняются одним скриптом. Повтор того же токена тем же
аккаунтом возвращает текущий снимок, даже если TTL уже прошёл; другому аккаунту
возвращается invite_consumed. Повтор работает, пока комната не закрыта.
Это восстановление после потерянного успешного HTTP-ответа, не повтор выдачи
секрета. Токен не хранится для восстановления ответа issue_invite: при его
потере владелец должен отозвать/перевыпустить приглашение. UI/endpoint перевыпуска
пока не реализованы; есть только revoke + issue как две отдельные операции.

## Отказоустойчивость и границы

- Перезапуск API не очищает Redis; тест recreation проверяет новый экземпляр
  адаптера, НЕ реальный kill/restart процесса API.
- Redis durability/AOF и рестарт сервера Redis ещё не проверены.
- Потеря Redis теряет комнаты/допуски, но будущие аккаунты должны жить в PG.
- Redis timeout после SET: результат неизвестен. Redeem/close/join можно повторять
  с прежними входными данными. Create с прежним ID вернёт room_id_exists:
  API должен сверить owner через snapshot, автоматического повтора здесь нет.
- issue_invite после timeout может оставить недоступный токен: необходимо revoke
  и явная перевыдача. Автоматически повторять его нельзя.
- Ошибки Redis не превращаются в нулевую загрузку и не допускают новые комнаты.
- Данные JSON содержат UUID и хеши: не писать их целиком в обычный лог.
- Совместный доступ нескольких API с разной конфигурацией не поддерживается.
- guarded пока принимает доверенный bool от будущего resource guard; сбор
  ресурсов, freshness, гистерезис и окна ещё отсутствуют.

Все Redis keys передаются через KEYS: https://redis.io/docs/latest/commands/eval/
